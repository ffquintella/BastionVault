# BastionVault Roadmap

Global entrypoint for roadmap and long-term planning in this repository.

The post-quantum crypto migration is complete. The default build uses a PQ-first, OpenSSL-free cryptographic stack.

## At a glance

| State | Count |
|---|---|
| Done | 60 |
| In progress | 7 |
| Todo | 7 |
| Removed | 1 |
| **Total tracked features** | **75** |

Active initiative: **Packaging & Distribution** ([roadmap](roadmaps/packaging-and-distribution.md)) — sequenced into four release waves; Waves 1 + 2 shipped (with Linux GUI bundler caveat), Wave 3 part-shipped (CLI installers on every platform; GUI installers, signing CI and the downloads website open).

## How to read this

- Tables below carry one row per tracked feature. **Status** leads with a progress checkbox followed by one of `Done`, `Todo`, `Partial`, `Removed`. **Notes** is a one-line summary with a spec link.
- **Checkbox legend:**
  - `[x]` — Done / shipped
  - `[/]` — In progress (includes `Partial` and `Skeleton`)
  - `[ ]` — Todo / not started
  - `[~]` — Removed / dropped
- A feature counts as Done (`[x]`) only when every phase in its linked spec is complete. Mixed-phase features stay `[/]`.
- Detailed phase notes for each feature live in the linked spec under [`features/`](features/) — the table is deliberately terse.
- Multi-phase initiatives that have closed out are summarised under [Completed Initiatives](#completed-initiatives) with full phase notes and outcomes.
- Open follow-ups that are not a top-line feature live under [Deferred sub-initiatives](#deferred-sub-initiatives).

The implicit `namespace-self` policy now grants the read-only resolvers (`policy/effective`, `dispatcher/preview`), `read` on `rustion/targets/+` (the bastion transport pin, else the hop degrades to unpinned TOFU), and the gated lifecycle (`session/open`, `v2/session/open`, `session/renew`, `session/kill`); `read_effective_policy` now fails closed on a denied resolve; the GUI launch gate honours the *effective transport tier* rather than the profile's stored `kind` (which defaults to `direct` on any profile predating the field, so a policy-brokered resource refused exactly the connect-only callers brokering protects); and `default-account` SSH profiles route through v2 by resolving the operator's account and rewriting the source to `ssh-engine`. **v1 `session/open` gained the per-resource gate** (option 3 of the spec's open question) so it could be granted too — it is the route brokered RDP and the client-resolved SSH kinds (LDAP / PKI / FIDO2) still take, which is why those used to fail closed inside a namespace. Its *unbound* shape (no `resource_id`: arbitrary target host + caller-supplied credential material, so no object to authorize against) now requires `sudo`, which the tenant baseline does not confer; the shared brokering engine moved to `brokered_session_open`, which authorizes nothing itself, so neither entry point can reach it ungated. **The gate itself was also blind to ownership and shares** — it probed only with `explain_capability`, whose identity-less dry-run makes scope-gated rules contribute nothing, so every caller reaching a resource through ownership or a share was refused and pushed onto the direct dial; it now falls back to `PolicyStore::readable_targets`, which re-runs the real evaluator with the owner / share / asset-group qualifiers hydrated. **The read-only resolvers are gated per resource too** (`may_view_resource`): they take a caller-supplied `resource_id`, so ungated they let any baseline holder enumerate the transport tier and fronting bastions of every resource — the check is deliberately broader than the connect gate (inventory record *or* the connect gate), because an SSH-engine profile needs no grant on the secret path, while tier-only resolution stays ungated. A bastion's `401 signature_invalid` refusal is **not** part of that split — the master keypair is deployment-global, so a namespaced envelope is signed with the same key a root one is; BV now appends the serial + fingerprint it signed with (plus the never-PKI-issued / rotated-without-re-approval cases) to `bastion_rejected` on session open/renew/kill and `authority/attest` so the mismatch against the bastion's pinned authority pubkey is readable from the error instead of looking like a namespace fault. NSCodec / RemoteFX / 8 bpp RLE / bitmap-cache references and SMB-through-Rustion documented as separate tracks. |

Adds `sys/identity/ns-assignment` storage + `v2/sys/identity/ns-assignment` CRUD + login-time fail-closed enforcement + GUI namespace multi-select on the Users/AppID pages. Design decisions and rationale documented in the spec. **A restricted principal can now actually sign in (Unreleased):** fail-closed enforcement alone locked tenant-only credentials out of every client without a namespace picker — the GUI login page sends no `X-BastionVault-Namespace` header, so the login resolved to root and was refused with `HTTP 403: Permission denied` on a correct password. An **unscoped** login (no header) now binds to the principal's *first assigned* namespace via `resolve_login_namespace_for_principal` / `default_login_namespace`, while a namespace named explicitly (incl. root as `"/"`) still fails closed — this cannot widen access, since the chosen path comes from the principal's own assignment. Paired with a new caller-introspecting **`GET /v2/sys/namespaces-self`** (`token_operable_resolved`-filtered list + `token_namespace`, granted by `default`/`namespace-self` because the `sys/namespaces` CRUD surface is sudo-gated and left a tenant unable to discover its own namespace): the GUI lands every login and every restored session on `token_namespace` (`namespaceStore.landSession`, otherwise the first fetch 403s at root) and the sidebar switcher renders only the namespaces the session can operate in, hiding itself when there is just one (**Unreleased:** with an admin fallback — a missing or single-entry answer unions in the sudo-gated `sys/namespaces` tree walk via `namespaceStore.widenWithAdminWalk`, because a root-bound admin with no assignment record, or any session against a server without the new route, otherwise lost the picker entirely). **The sign-in fix requires a server upgrade (0.38.4):** it is server-side only, so a cluster still on ≤0.38.1 keeps refusing tenant logins no matter what the desktop app runs — confirmed in production, where the `security` log read `login denied: principal 'userpass/felipe2' is not assigned to namespace ""` (the login had resolved to root). 0.38.4 also makes that refusal legible on the Audit page: it was recorded as `reason=invalid-token` at the mount-relative `login/<user>`, and now reads `reason=credential-refused` at the full `auth/<mount>/login/<user>`. **In progress** (remaining: `cert` / standalone-FIDO2 login binding, recursive GUI tree + rename).
